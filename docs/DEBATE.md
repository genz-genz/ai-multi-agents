## Brand Strategist

อ้างอิง: `docs/PROFILE.md` (ไม่ได้แก้ไฟล์นั้น) · มุมนี้พูดเรื่องแบรนด์อย่างเดียว ไม่แตะ UX หรือข้อโต้แย้งฝั่ง Devil's Advocate

### 1. Positioning

**แก่นของแบรนด์:** "พื้นที่ทักทายชิล ๆ ของคนไอทีที่ยังไม่รีบไปไหน"

เว็บนี้**ไม่ใช่** portfolio, ไม่ใช่ CV, ไม่ใช่บล็อก — ขายความเป็นตัวเองแบบไม่ต้องพยายาม จุดต่างจากเว็บ personal ทั่วไปที่ต้องอวดผลงาน คือความ **ซื่อตรงแบบขำ ๆ**: ยอมรับว่ายังไม่รู้จะไปไหน วันนึงวนอยู่แค่สามโหมด แล้วก็ไม่เป็นไร

- **ใครเป็นเจ้าของ:** คนทำงานไอที (เขียนโปรแกรม + ไอทีซัพพอร์ต) ที่ใช้ชื่อเล่น `12-Patana` — ตัวตนผ่านนิสัย ไม่ใช่ผ่านข้อมูลส่วนตัว
- **สัญญาของแบรนด์ (brand promise):** แวะมาแล้วยิ้มได้ ไม่ต้องอ่านเยอะ ไม่มีอะไรต้องขาย
- **บุคลิก:** เป็นกันเอง · ขำ ๆ กวน ๆ นิดหน่อย · ถ่อมตัว · มินิมอล (สะท้อนกับธีมขาวสะอาด)
- **กรอบความเป็นส่วนตัว = ส่วนหนึ่งของแบรนด์:** ไม่มีชื่อจริง รูปหน้า ที่ทำงาน — ความลึกลับนิด ๆ นี้ช่วยให้ "ชื่อเล่น + นิสัย" เป็นพระเอก

#### Headline vs Tagline

| | บทบาท | ข้อเสนอ |
|---|---|---|
| **Headline** | ประโยคแรกบนหน้าจอ บอกว่า "ที่นี่คืออะไร" ต้องสั้น จำง่าย | **Hello world** (คงไว้ตาม PROFILE) |
| **Tagline** | บรรทัดรองใต้ headline ขยายบุคลิก/อารมณ์ | "ยังไม่รู้จะไปไหน ขอฟังเพลงก่อน" |

เหตุผล:
- **"Hello world"** ทำงานสองชั้น — คนทั่วไปอ่านเป็นคำทักทาย คนไอทีจำได้ว่าเป็นโปรแกรมแรกที่ทุกคนเขียน → ส่งสัญญาณ "สายไอที" โดยไม่ต้องพูดตรง ๆ และสอดคล้องกับประโยคปิด Bio ("ก็ถือว่าเราได้ทักกันแล้ว — Hello world")
- **Tagline** ควรเป็นตัวบอกนิสัย เพราะ headline ยังกว้างเกินไป ในสามตัวเลือกจาก Brainstorm:
  - "ยังไม่รู้จะไปไหน ขอฟังเพลงก่อน" — **แนะนำ** ขำ ซื่อ และผูกกับฟีเจอร์ "เพลงสุ่มวันนี้" โดยตรง
  - "สามโหมดชีวิต" — ดีเป็น **หัวข้อ section** (Bio/About) มากกว่า tagline เพราะต้องอธิบายต่อ
  - "Hello world" — ซ้ำกับ headline ไม่ควรใช้เป็น tagline
- **ประโยคสุ่มหน้าแรก** ไม่ควรแทนที่ tagline — ให้ tagline คงที่เป็นหลักยึดแบรนด์ ส่วนประโยคสุ่มเป็น "เสียงประจำวัน" ที่เปลี่ยนได้

### 2. Audience

PROFILE ระบุ "ใครก็ได้ที่แวะมา" — กว้างเกินจะใช้เป็นแนวทางเขียนข้อความ เสนอแบ่งเป็นลำดับความสำคัญ:

1. **หลัก — เพื่อนและคนรู้จัก** ที่ได้ลิงก์ไปโดยตรง: อยากรู้ว่าช่วงนี้เป็นไงบ้าง อยากทิ้งข้อความใน guestbook → ต้องการความอบอุ่น ความขำ และช่องทางมีส่วนร่วมที่ง่าย
2. **รอง — คนในวงการไอที** ที่หลงมาเจอ: จะ "get" มุก Hello world / ทำตัวเหมือนยุ่ง ได้ทันที → ต้องการความรู้สึกว่า "คนนี้พวกเดียวกัน" ไม่ใช่รายการ skill
3. **ปลายทาง — คนแปลกหน้าที่อยากรู้จัก**: ต้องเข้าใจได้ภายในไม่กี่วินาทีว่าเจ้าของเป็นคนแบบไหน และรู้สึกว่าทักได้

**ไม่ใช่กลุ่มเป้าหมาย:** HR / recruiter / ลูกค้าที่หาคนจ้าง — ไม่ต้องปรับข้อความเพื่อคนกลุ่มนี้ (ถ้าวันหนึ่งอยากได้ ควรเป็นเว็บ/หน้าแยก ไม่ใช่ดัดแบรนด์นี้)

**นัยต่อการเขียน:** ใช้ภาษาไทยพูดคุยสบาย ๆ, ประโยคสั้น, มุกไอทีใช้ได้แต่ต้องไม่ทำให้คนนอกวงการงง (ชั้นแรกต้องอ่านรู้เรื่องเสมอ)

### 3. สามสารหลัก (Key messages)

เรียงตามความสำคัญ — ทุกข้อความบนเว็บ (headline, bio, ประโยคสุ่ม, การ์ด, empty state, 404 ในอนาคต) ควรสื่ออย่างน้อยหนึ่งข้อ

1. **"เราทักกันแล้วนะ" — เว็บนี้คือการทักทาย ไม่ใช่การขาย**
   ทุกอย่างวนกลับมาที่การเชื่อมต่อแบบเบา ๆ: Hello world เป็นคำทัก, guestbook เป็นคำทักกลับ ไม่มี call-to-action ให้จ้างงานหรือกดติดตาม
   *พิสูจน์ด้วย:* headline, ประโยคปิด Bio, guestbook ที่ใช้ชื่อเล่นอย่างเดียว

2. **"ชีวิตสามโหมด แล้วก็ไม่เป็นไร" — ซื่อตรงแบบขำ ๆ**
   เขียนโปรแกรม / ไอทีซัพพอร์ต / นั่งเฉย ๆ — สัดส่วนแล้วแต่ดวง ความถ่อมตัวและการยอมรับว่ายังไม่มีแผนใหญ่คือเสน่ห์ ไม่ใช่จุดอ่อน
   *พิสูจน์ด้วย:* Bio, "สถานะวันนี้" สุ่ม % (Nice), ประโยคสุ่มจาก Interests

3. **"ขอฟังเพลงไปก่อน" — ดนตรีคือจังหวะของที่นี่**
   เพลงเป็นสิ่งเดียวที่ชัดเจนในชีวิตตอนนี้ จึงควรเป็นสีสันหลักของเว็บ ทำให้ทุกครั้งที่แวะมามีอะไรใหม่ ๆ แม้เจ้าของไม่ได้อัปเดตเลย
   *พิสูจน์ด้วย:* tagline, การ์ด "เพลงสุ่มวันนี้", ลิงก์ "ฟังต่อ"

### 4. Guardrails ของแบรนด์

- **ทำ:** สั้น · ขำแบบไม่ประชด · มินิมอล · ใช้ชื่อเล่น `12-Patana` สม่ำเสมอ
- **ไม่ทำ:** อวด skill/ผลงาน · ข้อความทางการ/คำศัพท์ corporate · เติมข้อมูลส่วนตัวที่ไม่อยู่ใน PROFILE · มุกที่ดูถูกผู้เข้าชมหรือตัวเองแรงเกินไป
- **ความกวนต้องมีขอบเขต:** กวนแบบ "นั่งเฉย ๆ อย่างมีสไตล์" ได้ แต่ข้อความสำคัญ (เช่น error ของ guestbook, กติกาห้ามลิงก์) ต้องชัดก่อนขำ

### คำถามเปิดสำหรับรอบ debate

- Tagline ควรเป็นภาษาไทยล้วน หรือผสมอังกฤษเพื่อให้เข้ากับ "Hello world"?
- ถ้าการ์ดเพลงถูกซ่อน (API ล่ม) สาร #3 จะเหลือแค่ tagline — พอหรือไม่?

## Devil's Advocate

อ้างอิง: `docs/PROFILE.md` · ส่วน Brand Strategist ด้านบน · โค้ดปัจจุบัน `src/lib/db.ts`, `src/pages/contact.astro`, `src/pages/guestbook.astro` (อ่านอย่างเดียว ไม่ได้แก้) · มุมนี้โจมตี 3 เรื่อง: **privacy · credibility · scope creep**

### 1. ความเสี่ยง (เรียงจากหนักไปเบา)

| # | ความเสี่ยง | หมวด | ทำไมน่ากังวล |
|---|---|---|---|
| R1 | **ฟอร์ม Contact เก็บอีเมลผู้เข้าชม แต่ไม่มีใครอ่าน** | privacy | ตาราง `contact_messages` เก็บ `name + email + message` ถาวรใน SQLite แต่ Brainstorm บอก "ไม่มีแอดมิน / เจ้าของไม่อัปเดตเอง" → เก็บข้อมูลส่วนบุคคลของคนอื่นโดยไม่มีจุดประสงค์ ไม่มีคนตอบ ไม่มีนโยบายลบ = ภาระ PDPA ฟรี ๆ และขัดกับหลัก "ไม่เก็บอีเมล" ที่ตั้งไว้กับ guestbook |
| R2 | **Guestbook ไม่มีทางลบข้อความ** | privacy / spam | "ห้ามลิงก์ + จำกัดความยาว" กันได้แค่ spam ดาด ๆ แต่ไม่กันคนพิมพ์ชื่อจริง/เบอร์ของ**คนอื่น** คำหยาบ หรือแซวเจ้าของด้วยข้อมูลส่วนตัว (doxxing) — เมื่อหลุดขึ้นเว็บแล้วไม่มีแอดมิน = ค้างอยู่หน้าเว็บจนกว่าจะมีคนเข้า server ไปแก้ DB เอง |
| R3 | **"จำกัดความถี่" ขัดกับ "ไม่เก็บ IP"** | spam | ถ้าไม่เก็บ IP เลย rate limit จะทำได้แค่ global (ทั้งเว็บ N ข้อความ/นาที) ซึ่ง bot คนเดียวก็ยึดโควตาทั้งเว็บได้ · ต้องตัดสินให้ชัดว่าใช้ IP ใน**หน่วยความจำชั่วคราว** (ไม่ลง DB ไม่ log) ได้หรือไม่ ไม่งั้น backend จะเดาเอง |
| R4 | **"ห้ามลิงก์" ถูกเลี่ยงง่าย** | spam | `example[.]com`, `bit ly/xx`, `wwwดอทcom`, Line ID, เบอร์โทร — regex จับ `http` อย่างเดียวไม่พอ และถ้าไล่จับทุกแบบก็ scope creep · ต้องยอมรับว่ากันได้ไม่ 100% → จึงต้องมีทางลบ (R2) |
| R5 | **ข้อมูลติดต่อปลอม = เสียความน่าเชื่อถือ** | credibility | `demo@example.com` + github/linkedin เป็น `—` ถ้าขึ้นหน้าเว็บจะดูเหมือนเว็บยังไม่เสร็จ (หรือแย่กว่านั้น คนส่งอีเมลไปแล้วเด้ง) · ขัดกับสาร "เราทักกันแล้วนะ" |
| R6 | **การ์ด "เพลงสุ่มวันนี้" overclaim รสนิยมเจ้าของ** | credibility | เพลงมาจาก**ชาร์ตไทย** ไม่ใช่สิ่งที่ 12-Patana ฟังจริง แต่ tagline "ขอฟังเพลงก่อน" ทำให้คนอ่านเข้าใจว่าเป็นเพลย์ลิสต์ของเจ้าของ → ถ้ามีเพลงที่เจ้าของไม่ชอบ/เนื้อหา explicit ขึ้นมา เจ้าของรับหน้าแทน · ต้องติดป้ายแหล่งที่มา |
| R7 | **พึ่ง API ภายนอกตอน SSR** | credibility / scope | เว็บเป็น SSR ทุก request — ถ้า fetch Apple Music RSS ไม่มี timeout หน้าแรกจะช้าตาม API (ไม่ใช่แค่ "ซ่อนการ์ด") · endpoint/ToS/รูป artwork (hotlink) เปลี่ยนได้โดยไม่แจ้ง · ยังไม่ได้เช็ก endpoint จริงตามที่ Brainstorm เขียนไว้เอง |
| R8 | **ข้อความสุ่ม/สถานะ % อาจสร้างประโยคแปลก** | credibility | แม่แบบ × Interests ประกอบอัตโนมัติ → ได้ประโยคไวยากรณ์เพี้ยน หรือ "สถานะวันนี้: ทำตัวเหมือนยุ่ง 97%" ที่คนนอกอ่านเป็นการประชดที่ทำงาน/ลูกค้า (Bio บอกว่าทำไอทีซัพพอร์ต) |
| R9 | **ข้อความเทคนิครั่วบนหน้าเว็บ** | credibility | ตอนนี้ `contact.astro` แสดง "ฟอร์มนี้โพสต์ไปที่ `POST /api/contact`" และ guestbook แสดง `/api/guestbook` — คนทั่วไปอ่านไม่รู้เรื่อง และเผยพื้นผิว API ให้ bot · เช่นเดียวกับข้อความที่อ้างถึงคอร์ส (guard `public-site.test.ts`) |
| R10 | **ข้อมูล guestbook หายตอน redeploy** | credibility | SQLite อยู่ใน `$DATA_DIR` — ถ้าไม่ได้ mount volume ตอน ship คำทักทายทั้งหมดหายเงียบ ๆ คนที่เคยเขียนกลับมาไม่เจอ |
| R11 | **Scope creep จากรายการ Nice/Later** | scope | ปุ่มสุ่มใหม่ (ต้องมี client JS/endpoint ใหม่), สถานะ %, 404 ขำ ๆ, ตัวนับ, โหมดมืด — แต่ละข้อดูเล็ก แต่รวมกันเพิ่มงานทั้ง FE และ BE ข้าม harness ขณะที่ของ Must ยังเป็น stub `NOT_IMPLEMENTED` อยู่ทั้งหมด |

### 2. ควรตัดก่อน ship (v1)

- **ตัดฟอร์ม Contact + ตาราง `contact_messages` ออกจาก v1** (แก้ R1, R5) — แบรนด์บอกเองว่า "guestbook คือคำทักกลับ" ไม่จำเป็นต้องมีช่องทางส่วนตัวที่ไม่มีใครอ่าน · ถ้าอยากมีช่องทางติดต่อจริง ใส่ลิงก์ที่เจ้าของยืนยันแล้ว (เช่น GitHub) ในรอบถัดไป · ⚠️ route/stub `insertContact` เป็นของ backend (OpenCode) และมี test ใน `tests/labs` — การตัดต้องเขียนเป็น decision + handoff ไม่ใช่ลบเอง
- **ซ่อนหัวข้อ Contact จนกว่าจะมีข้อมูลจริง** — ห้ามแสดง `demo@example.com` หรือ `—`
- **ตัด Nice ทั้งหมด:** ปุ่ม "สุ่มใหม่", "สถานะวันนี้" %, ลิงก์ "ฟังต่อ" → ย้ายไป backlog
- **ตัด Later ทั้งหมด:** 404 ขำ ๆ, ตัวนับคนทัก, โหมดมืด
- **ลดการ์ดเพลงเป็น "ไม่บล็อก ship"** — ตอบคำถามเปิดของ Brand Strategist: *พอ* — tagline "ยังไม่รู้จะไปไหน ขอฟังเพลงก่อน" แบกสาร #3 ได้เองแล้ว การ์ดเพลงจึงควรเป็นของเสริมที่ ship ได้ทั้งมีและไม่มี ถ้า endpoint ยังไม่ได้เช็กหรือยังไม่มี timeout/cache ภายในรอบ FE → ship โดยไม่มีการ์ด
- **ลบข้อความเทคนิคบนหน้า** (`POST /api/...`) ออกจาก markup ที่ render

### 3. ต้องเพิ่มใน Must ของ Brainstorm

ของที่ Brainstorm ยังไม่มี แต่ถ้าไม่มี = ไม่ควร ship:

1. **Guestbook มีทางลบ/ปิดได้โดยไม่ต้องมีหน้าแอดมิน** — เช่น env `GUESTBOOK_READONLY=1` (ปิดรับข้อความใหม่ทันที) + ขั้นตอนลบข้อความด้วย sqlite ที่เขียนไว้ใน `docs/` · (แก้ R2, R4)
2. **ประกาศใต้ฟอร์ม guestbook:** "ข้อความจะแสดงสาธารณะ · ใช้ชื่อเล่นเท่านั้น · ห้ามใส่ข้อมูลส่วนตัวของตัวเองหรือคนอื่น" — ชัดก่อนขำ (ตาม guardrail แบรนด์)
3. **ตัดสินเรื่อง rate limit ให้ชัดใน DECISIONS** — ข้อเสนอ: IP ใช้ได้เฉพาะใน memory ของ process (หมดอายุไม่กี่นาที) ห้ามลง DB/log · กำหนดตัวเลข: ชื่อ ≤ 30 ตัวอักษร, ข้อความ ≤ 280, ≤ 1 ข้อความ/นาที/ผู้ส่ง · (แก้ R3)
4. **Validation ฝั่ง server เป็นหลัก** — escape ตอนแสดง, trim, ปฏิเสธข้อความว่าง, ปฏิเสธ pattern ลิงก์พื้นฐาน (`http`, `www.`, `.com/.co/.th` ติดตัวอักษร) — client-side เป็นแค่ UX
5. **การ์ดเพลง (ถ้า ship):** timeout ≤ 2 วินาที · cache ฝั่ง server ≥ 1 ชม. · ล้ม = ซ่อนการ์ด · ติดป้าย "สุ่มจากชาร์ตเพลงไทย Apple Music" ชัดเจน · ไม่ hotlink ถ้า ToS ไม่อนุญาต · (แก้ R6, R7)
6. **แม่แบบประโยคสุ่มเป็น whitelist ที่อ่านตรวจแล้ว** — ทุกแม่แบบ × ทุก Interest ต้องอ่านรู้เรื่อง ไม่พาดพิงงาน/ที่ทำงาน · มี unit test ไล่ทุกคอมบิเนชัน (แก้ R8)
7. **Privacy check ก่อน ship** — ไม่มีชื่อจริง/อีเมล/placeholder บนหน้า, ไม่มีข้อความเทคนิคหรือคำที่อ้างถึงคอร์ส, `public-site.test.ts` เขียว (แก้ R5, R9)
8. **Volume สำหรับ `DATA_DIR` ระบุใน `docs/SHIP.md`** และทดสอบว่า restart แล้ว guestbook ยังอยู่ (แก้ R10)

### คำถามเปิดสำหรับรอบ debate

- ยอมตัด Contact ออกทั้งหมด หรืออยากได้ช่องทางติดต่อจริงช่องเดียว (ลิงก์ ไม่ใช่ฟอร์ม)?
- ยอมให้ใช้ IP ใน memory ชั่วคราวเพื่อ rate limit ได้ไหม — หรือยอมรับ global limit ที่อ่อนกว่า?
- ใครเป็นคนลบข้อความ guestbook เมื่อเกิดเรื่อง และทำภายในกี่ชั่วโมง?

## UX Critic

อ้างอิง: `docs/PROFILE.md` + ส่วน Brand Strategist ด้านบน (ไม่ได้แก้ทั้งสองส่วน) · มุมนี้คือ end-user ที่เปิดลิงก์จากมือถือ ไม่ใช่เจ้าของเว็บ · ไม่มีโค้ด — ข้อเสนอ IA + microcopy เท่านั้น

### 1. ปัญหาหลัก: 4 หน้า (Home · About · Interests · Contact) ไม่ตรงกับของที่มีจริง

| หน้า | เนื้อหาที่มีใน PROFILE | มุมผู้ใช้ |
|---|---|---|
| Home | Headline · tagline · ประโยคสุ่ม · การ์ดเพลง | ✅ มีของพอ และเป็นจุดที่ "มีอะไรใหม่" ทุกครั้ง |
| About | Bio 2 ย่อหน้า | ⚠️ สั้น อ่านจบใน 20 วินาที — ไม่ผิด แต่บางเกินเป็นหน้าเดี่ยว |
| Interests | 3 bullet (ฟังเพลง · นั่งเฉย ๆ · ทำตัวเหมือนยุ่ง) | ❌ กดเข้าไปเจอ 3 บรรทัด = รู้สึกว่า "หน้ายังไม่เสร็จ" มุกดีแต่เสียแตะหนึ่งครั้งไปเปล่า ๆ |
| Contact | email (demo) · github `—` · linkedin `—` | ❌ 2 ใน 3 ช่องเป็นขีด → สื่อว่า "ไม่อยากให้ติดต่อ" ขัดกับสาร #1 "เราทักกันแล้วนะ" |
| **Guestbook** | Must ใน Brainstorm | ❌ **ไม่อยู่ใน 4 หน้าเลย** — ทั้งที่เป็นฟีเจอร์เดียวที่ผู้เข้าชมมีส่วนร่วมได้ |

**สรุป:** Interests และ Contact **ไม่คุ้ม**เป็นหน้าแยก ส่วน Guestbook ที่คุ้มที่สุดกลับไม่มีที่อยู่

### 2. ข้อเสนอ IA (เลือกหนึ่ง)

**A. แนะนำ — 3 หน้า**

```text
Home        headline · tagline · ประโยคสุ่ม · การ์ดเพลง · (Nice) สถานะวันนี้ · ลิงก์ชวนไปทักทาย
About       Bio ครบทุกย่อหน้า · "สามโหมดชีวิต" · Interests เป็นชิป/บรรทัดสั้นท้าย Bio
ทักทาย      Guestbook (ฟอร์ม + ข้อความล่าสุด) · email บรรทัดเดียวด้านล่าง
```

- Interests ย้ายเข้า About — ต่อท้าย Bio ได้ลื่นเพราะ Bio พูดถึง "ฟังเพลง / ทำตัวเหมือนยุ่ง" อยู่แล้ว
- Contact รวมกับ Guestbook — ผู้ใช้ส่วนใหญ่ (เพื่อน) อยาก "ทิ้งข้อความ" มากกว่าส่งอีเมล · อีเมลเป็นทางเลือกรอง
- nav 3 ข้อความสั้นพอดีบนจอ 360px ไม่ต้องมี hamburger

**B. ทางเลือก — หน้าเดียวเลื่อนยาว + anchor** (`#about` `#guestbook`)
เหมาะกับเนื้อหาที่น้อยมาก แต่ Home จะยาวบนมือถือและประโยคสุ่ม/การ์ดเพลงถูกดันขึ้นไปเร็ว — ใช้ถ้าทีมอยากตัด nav ทิ้ง

**ถ้าต้องคง 4 หน้าตามแผนเดิม:** อย่างน้อยให้เปลี่ยน Contact → "ทักทาย" (มี guestbook) และซ่อนช่องที่เป็น `—` แทนการแสดงขีด

### 3. อ่านง่ายบนมือถือ — จุดที่ต้องระวัง

- **ข้อความสำคัญอยู่เหนือพับ:** บน Home ลำดับควรเป็น headline → tagline → ประโยคสุ่ม → การ์ดเพลง · อย่าให้การ์ดเพลง (ที่อาจถูกซ่อน) เป็นสิ่งแรก ไม่อย่างนั้นตอน API ล่มหน้าจะดู "โหว่"
- **Bio ภาษาไทยยาว:** แบ่งย่อหน้าตาม PROFILE ห้ามรวบเป็นก้อนเดียว · บรรทัดไม่ยาวเกิน ~35–40 ตัวอักษรไทยบนมือถือ · ระยะบรรทัดโปร่ง (ภาษาไทยมีสระบน/ล่าง ชนกันง่าย)
- **ปุ่ม "สุ่มใหม่" / "ฟังต่อ" / "ส่ง":** เป้าแตะใหญ่พอสำหรับนิ้วโป้ง และแยกให้ชัดว่า "ฟังต่อ" = ออกไป Apple Music (บอกล่วงหน้า ไม่ให้เด้งออกแบบงง ๆ)
- **การ์ดถูกซ่อน = ไม่เหลือช่องว่าง:** layout ต้องไม่ทิ้งกล่องเปล่าไว้ (สอดคล้องกับ Brainstorm "API ล่ม = ซ่อนการ์ด")
- **ฟอร์ม guestbook บนมือถือ:** บอกขีดจำกัดตัวอักษรก่อนพิมพ์ (ตัวนับ) ไม่ใช่รอให้ error หลังกดส่ง · แป้นพิมพ์ไม่ควรบังปุ่มส่ง
- **ธีมขาวมินิมอล:** ขาวล้วนเสี่ยง contrast ต่ำถ้าใช้ตัวอักษรเทาอ่อน — ตัวเนื้อหาต้องเข้มพอ อ่านกลางแดดได้

### 4. Microcopy — ข้อเสนอ

โทนตาม Brand guardrail: ชัดก่อนขำ โดยเฉพาะ error และกติกา

| จุด | ปัจจุบัน/ความเสี่ยง | เสนอ |
|---|---|---|
| nav | Home / About / Interests / Contact (อังกฤษล้วน ทางการ) | **หน้าแรก · รู้จักกัน · ทักทาย** (หรือคงอังกฤษทั้งชุดให้เข้ากับ "Hello world" — แต่อย่าผสมครึ่ง ๆ) |
| หัวการ์ดเพลง | "เพลงสุ่มวันนี้" | คงไว้ — ชัดอยู่แล้ว · ใต้ชื่อเพลงบอกที่มา "จากชาร์ตไทย Apple Music" สั้น ๆ |
| ลิงก์ออก | "ฟังต่อ" | **"ฟังต่อบน Apple Music ↗"** — บอกปลายทางให้รู้ก่อนกด |
| ปุ่มสุ่ม | "สุ่มใหม่" | คงไว้ · หรือ "ขออีกเพลง" ถ้าอยากกวนนิดหน่อย |

| ช่องชื่อ guestbook | — | label **"ชื่อเล่น"** + hint "ชื่อเล่นพอ ไม่ต้องชื่อจริง" (ย้ำ privacy ให้ผู้เข้าชมด้วย) |
| ช่องข้อความ | — | placeholder "ฝากอะไรไว้ก็ได้ สั้น ๆ พอ" · ตัวนับ "0/200" (ตัวเลขจริงรอ D-id) |
| กติกาใต้ฟอร์ม | ห้ามลิงก์ / จำกัดความถี่ (อยู่แค่ใน Brainstorm) | **"ข้อความเท่านั้น ใส่ลิงก์ไม่ได้นะ"** — บอกก่อนพิมพ์ |

### 5. ข้อขัดแย้งที่ควรปิดในรอบ debate

- **Guestbook ไม่อยู่ใน IA 4 หน้า** — ต้องตัดสินก่อน Lab 04 ว่าอยู่หน้าไหน
- **Interests เป็นหน้าเดี่ยวหรือส่วนหนึ่งของ About?** (UX เสนอรวม)
- **nav ภาษาไทยหรืออังกฤษ?** — เชื่อมกับคำถามเปิดของ Brand เรื่อง tagline ไทย/อังกฤษ ควรตัดสินชุดเดียวกัน
- **Contact ที่เป็น `—`:** ซ่อน หรือเติมข้อมูลจริง (ถ้าเติม ต้องผ่านเงื่อนไข Privacy ใน PROFILE ก่อน)
- **ตัวเลขจำกัดความยาว/ความถี่ของ guestbook** — microcopy ต้องใช้ตัวเลขเดียวกับที่ backend บังคับ
